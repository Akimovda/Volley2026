## Организатор Pro — привязка функций и уведомления об окончании (2026-09-30)
- **Личный бот**: `UserNotificationChannel::resolveToken()` отдаёт токен только при активном Pro владельца канала (`user->isOrganizerPro()`), иначе `null` → `ChannelPublisherFactory` берёт системного бота. Бот/токен остаются подключёнными; Telegram требует, чтобы системный бот был админом канала, иначе анонсы не дойдут (FAQ на `/organizer-pro` это говорит).
- **Виджет на сайт**: `WidgetPublicController` (iframe и `/api/widget/events`) проверяет Pro владельца (`ownerHasPro()`); без Pro — iframe показывает `widget/unavailable.blade.php`, JSON отдаёт 403 `{ok:false, code:'subscription_inactive', error}` + CORS-заголовок (иначе браузер стороннего сайта не прочитает ответ), JS-скрипт рисует серое сообщение. Ключ и настройки не трогаются — после продления виджет оживает сам. Порядок проверок: ключ → домен → Pro.
- **`organizer-pro:notify-expiring`** (`dailyAt('09:00')`, `routes/console.php`): пороги «осталось N дней» по тарифу — year/quarter 30 и 7, month (и нестандартные) 7 и 1, trial 1; плюс «закончилась» и перевод `active→expired` (раньше `expireOld()` нигде не вызывался). Повторы исключает `organizer_subscriptions.expiry_notice_days` (последний отправленный порог, 0 = закончилась); шлётся только самый близкий применимый порог. **Давно закончившиеся (>3 дней) закрываются молча** — иначе первый запуск разослал бы «закончилась» по подпискам месячной давности (на проде были 3 такие). Типы шаблонов `organizer_pro_expiring`/`organizer_pro_expired` (is_active=false, содержимое из кода, группа «Организатор Pro» в админке).
- **Оплата Pro (2026-09-30, закрыта дыра «бесплатная активация»)**: `OrganizerProController::activate` принимает ТОЛЬКО `trial` (раньше любой авторизованный мог включить month/quarter/year без оплаты, да ещё с записью Payment `paid`). Платные тарифы: `pay()` → `OrganizerSubscriptionService::createPending()` (pending-подписка + pending-платёж, цены из `platform_payment_settings.organizer_pro_*_rub`; неоплаченные старые заявки отменяются, отправленные на проверку — сохраняются) → «Я оплатил» (`confirmPayment`, уведомление админу `organizer_pro_payment_pending` со ссылкой) → `AdminSubscriptionController::confirmPro` (GET `/admin/subscriptions/pro/{payment}/confirm`, `activatePending()`: срок прибавляется к остатку, Payment `paid`+`org_confirmed_at` — по ним считается выручка на дашборде) + уведомление организатору `organizer_pro_paid_activated`. Заявки Pro видны в блоке «ожидают подтверждения» на админ-дашборде вместе с Premium (поле `kind`). Конструкция зеркалит Premium (`confirmPending`). На проде до фикса были 2 платные подписки на год без платежа (user 1 и 839, выданы вручную/самоактивацией) — не трогали.
- **Ручная выдача Pro из админки** (`/admin/users/{id}`, карточка «Организатор Pro»): `AdminSubscriptionController::grantPro` → `activate($user, $plan, 'admin')`, срок прибавляется к остатку, `amount_rub=NULL`, без Payment (в выручку не попадает), запись `user.pro.grant` в `admin_audits` (причина — в `meta.note`), пользователю уведомление `organizer_pro_granted`. Там же кнопка «Отключить Pro» (`subscriptions.pro_deactivate`).
- **Pro-аналитика за гейтом (2026-10-02)**: middleware `organizer.pro` (`EnsureOrganizerPro`, админ проходит всегда) на `/org/players` (+`audience`, экспорты CSV/PDF) и `/org/tournament-analytics`. Без Pro — страница `organizer-pro/analytics-locked` (403), для JSON/AJAX — 403 `subscription_inactive`. `/org/dashboard` остаётся базовым для всех организаторов (ссылки на закрытые страницы там с 🔒, флаг `$proAnalytics`). Раньше аналитика была открыта всем, хотя тариф её «продавал». Новая Pro-страница аналитики — вешать `->middleware('organizer.pro')`. После деплоя: `route:cache`+`config:cache`+`reload php8.3-fpm` одним блоком (новый middleware-класс + алиас в `bootstrap/app.php`).
- **Тарифы Pro (2026-10-02): в продаже только `trial` (7 дней), `half` (6 мес = 180 дн, 3490 ₽) и `year` (4990 ₽).** Цены — `platform_payment_settings.organizer_pro_half_rub`/`organizer_pro_year_rub` (правятся в админке «Платёжная система»), читает `OrganizerSubscriptionService::priceRub()` и `OrganizerProController::index()`; дефолты — `OrganizerSubscription::planPrice()`. `month`/`quarter` из продажи убраны (`pay()` валидирует `in:half,year`), но остались в `planLabel/planDays/planPrice`, колонках цен и в ручной выдаче (`admin.users.pro.grant` принимает month/quarter/half/year) — по ним есть живые подписки, не удалять. `NotifyOrganizerProExpiring::thresholdsFor()`: half/year/quarter → [30, 7]. Миграция `2026_10_02_100000` выставила на проде half=3490, year=4990. Карточки на `organizer-pro/index.blade.php` — `col-lg-4`, выделен `year`. **Ловушка вёрстки**: блок после `.row` (у него `margin-bottom:-2rem`) слипается с рядом карточек — там нужен явный `margin-top` (блок «Как подключить», White Label).
- Продление = `OrganizerSubscriptionService::activate()`: старые active → cancelled (не попадают в команду), новая считается от `now()` — остаток старой подписки НЕ прибавляется (существующее поведение, не менялось).
- Тестировать команду без реальных рассылок: подписки тестовым ботам (`is_bot`, без каналов) внутри `DB::beginTransaction()`/`rollBack()` — очередь `database` + `afterCommit` на откате ничего не отправит.

## Premium (игроки) — продление и уведомления об окончании (2026-09-30)
- **Тарифы Premium (2026-10-02): в продаже `trial` (7 дней, бесплатно), `half` (6 мес = 180 дн, 2490 ₽) и `year` (3990 ₽).** Цены — `platform_payment_settings.premium_half_rub`/`premium_year_rub` (админка «Платёжная система», блок «Premium (игроки)»); единая точка — `PremiumSubscription::planPriceRub()` (рубли) / `planPriceMinor()` (копейки, для `Payment.amount_minor`), используют `pay()`/`renew()`, а `PremiumController::index()` отдаёт в `/premium` `$priceHalf/$priceYear/$yearSaving` («Выгода N%» год vs 2×half считается сама, при ≤0 скрывается). `month`/`quarter` из продажи убраны (`pay`/`renew` валидируют `in:half,year`), но в `planDays/planLabel/planPriceMinor` (цены 199/499 ₽ захардкожены) и в `match` шаблонов остались — для уже существующих подписок и pending-заявок; **убирать их из `match` в blade нельзя** (`UnhandledMatchError` на старой записи). `premium:notify-expiring`: half → [30, 7]. В Blade-директиву `@foreach([...])` не класть конкатенации/тернарники — собирать массив в `@php`. Миграция `2026_10_02_110000`.
- **Покупка/продление** идут через `pending` + подтверждение админом (`PremiumService::confirmPending`), бесплатной самоактивации платных тарифов нет (в отличие от Организатор Pro). `confirmPending`: при ещё действующей подписке срок = её `expires_at` + дни тарифа (остаток не теряется), иначе от даты платежа; правило «давно зависший pending не даёт доступ» сохранено. `PremiumService::renew()` (тоже прибавляет к остатку) контроллером не используется.
- **`premium:notify-expiring`** (`dailyAt('09:05')`): пороги 30/7 (год, квартал), 7/1 (месяц и прочие), 1 (пробный); дедуп — `premium_subscriptions.expiry_notice_days` (0 = закончилась). Текст упоминает снятие подписок на игроков/автозаписей, только если они у игрока есть.
- **«Premium закончился»** шлёт не отдельная команда, а `PremiumService::expireAll()` (`premium:expire`, hourly) — иначе hourly-команда успела бы перевести подписку в `expired` раньше. В тексте — сколько подписок на игроков и автозаписей снято (считается ДО удаления). Давно закончившиеся (>3 дней) закрываются молча; у пользователей с другой ещё действующей подпиской фичи не снимаются. Шаблоны `premium_expiring`/`premium_expired` (группа «Premium» в админке).

## Онлайн-оплата через ЮKassa: Pro/Premium, мероприятия, реклама (2026-10-14, на проде, платежи подтверждены владельцем)
- **Три контура, разные ключи**: Pro/Premium и реклама — ключи платформы (`platform_payment_settings`, секрет хранится `encrypt()` → `YookassaService::platformSecret()` расшифровывает, фолбэк на открытый текст); оплата мероприятий — ключи ОРГАНИЗАТОРА (`payment_settings`, секрет в БД открытым текстом, хотя UI пишет «хранится зашифрованным» — текст неверный, не правили). Кнопки/потоки включаются при `method='yoomoney'`; при `tbank_link`/`sber_link` остаётся ручной поток «Я оплатил».
- **Pro/Premium**: `PlatformPaymentController::pay` → платёж ЮKassa, возврат `platform.payment.return` перепроверяет статус у ЮKassa; зачисление — `PlatformPaymentService::settle()` (идемпотентно, из вебхука и возврата). Мероприятия: `PaymentService::createForRegistration` создаёт платёж ЮKassa (`createEventPayment`), сбой не роняет запись. Реклама: `createAdPayment`.
- **Вебхуки**: любой из `/yookassa/webhook` и `/payments/yoomoney/webhook` обслуживает все типы (платформа / организатор / реклама). **Оба обязаны быть в `validateCsrfTokens(except)` в `bootstrap/app.php`** — `withoutMiddleware(VerifyCsrfToken)` в Laravel 12 не работает (419). URL прописывается в кабинете ЮKassa каждого магазина.
- **Чек (receipt)**: магазин ЮKassa может требовать `receipt` в каждом платеже («Receipt is missing or illegal»). Флаг/НДС/СНО — `yookassa_receipt_enabled|vat_code|tax_system_code` в `platform_payment_settings` (прод: включено, без НДС, СНО не передаётся — АУСН) и в `payment_settings` организатора (по умолчанию выключено); общий partial `payment/_receipt_fields`. vat_code: 1 без НДС, 7=5%, 8=7%, 11=22%; tax_system_code только 1–6 (у АУСН/НПД кода нет — не передавать).
- **Комиссия и налог** (`App\Support\PaymentPricing`): три набора настроек — мероприятия (`''`, `payment_settings`), Premium+Pro (`sub_`), реклама (`ad_`). Налог: % + режим «в цене»/«сверху» + система налогообложения (`TAX_SYSTEMS`: УСН 6/15, АУСН 8/20, НПД, ОСН — подставляет ставку, минимум 3% АУСН не считается). Комиссия ЮKassa зависит от способа (карты/ЮMoney/SberPay/T-Pay 3,8%, СБП 2,2%; `fee_methods` JSON, пусто = способ не предлагается). Режим «сверху» → `needsChoice()`: платёж создаётся БЕЗ комиссии/без вызова ЮKassa, игрок выбирает способ на `payment/choose_method` (`OnlinePaymentController`, роуты `payments.online.*`, `ads.pay.*`), затем сумма пересчитывается от `yoomoney_meta.base_minor` и создаётся платёж с `payment_method_data`. `payments.fee_minor/tax_minor` — только надбавки «сверху»; `amount_minor` = итог (выручка в дашборде считается вместе с надбавками). Для рекламы `events.ad_yookassa_payment_url` = адрес страницы выбора способа.
- **Выбор способа оплаты игроком (2026-10-14)**: галочка `offer_choice` + отметки `offer_methods` (cash/tbank_link/sber_link/yoomoney, только реально настроенные) в `payment_settings` (организатор, мероприятия; есть «наличными») и `platform_payment_settings` (админка; Pro/Premium/реклама). Меньше двух способов = выбора нет, действует прежний `method`/`payment_method` события. `PaymentSetting::offeredFor()` / `PlatformPaymentSetting::offeredMethods()/resolveMethod()`, справочник `App\Support\PaymentMethods`. Попап — `window.askPaymentMethod` + генерик-обработчик `form[data-pay-choices]` в конце `public/assets/script.js`; запись на мероприятие (AJAX `data-ajax-join`) спрашивает способ ДО запроса, сервер (`EventRegistrationController::storeOccurrence`) требует допустимый `payment_method` (иначе 422) и подменяет `$event->payment_method` только в памяти. Не применяется: организатору, записи по абонементу, автозаписям (Premium/абонемент/лист ожидания — там способ события), командным турнирным платежам. Платежи Pro/Premium хранят выбранный способ в `payments.method`; блоки «ожидает оплаты» смотрят на `payments.method`, а не на текущие настройки платформы. Реклама: `events.ad_payment_method`, выбор на странице мероприятия (`ads.pay.method`).
- **Командные платежи турниров (2026-10-14)**: `TournamentPaymentService::createTeamPayment/createMemberPayment` раньше НИГДЕ не вызывались (вызов и запрет жеребьёвки из e3f461b4 потерялись при слияниях) — теперь `TournamentTeamService::submitApplication(..., ?$paymentMethod)` после коммита вызывает `ensurePayments()` (режим «за команду» — платёж капитана; «каждый сам» — платежи подтверждённых участников, выбранный способ — только капитану). Капитан выбирает способ попапом на форме подачи заявки (`data-pay-choices`, сервер требует допустимый `payment_method`); игрок может позже оплатить/сменить способ — `POST tournamentTeams.pay` (`applyMethod()`, нельзя после «Я оплатил»/оплаты). UI — `tournaments/teams/_pay_controls`. Онлайн: `startOnline()` → `YookassaService::createEventPayment`; зачисление — `PaymentService::markPaid()` для `payment->team_id` зовёт `TournamentPaymentService::handleYoomoneyPaid()` (статус команды/участника). Оплата жеребьёвку НЕ блокирует (решение владельца). Платежи участников, добавленных ПОСЛЕ подачи заявки (per_player), автоматически не создаются — только по кнопке «Оплатить».
- **Лист ожидания → платное мероприятие (2026-10-14)**: `WaitlistService::autoBookNext` для не-наличных способов даёт `config('waitlist.payment_hold_minutes')` (30) минут: `payments.expires_at` + `yoomoney_meta.waitlist_hold`, уведомление `waitlist_payment_required` (кнопка «Перейти к оплате»: онлайн → ссылка ЮKassa/`payments.online.choose`, ссылки Т-Банк/Сбер → страница мероприятия). `payments:expire-waitlist-holds` (everyMinute): просрочено и нет «Я оплатил» → онлайн-платёж сперва сверяется с ЮKassa (`succeeded` → `markPaid`), иначе платёж `expired`, регистрация отменяется через Eloquent `save()` (Observer освобождает место следующему), уведомление `waitlist_payment_expired`. Другие автозаписи (Premium/абонемент) и обычные платежи за мероприятия таймер НЕ получают (маркер только у листа ожидания).
- **Не сделано**: автоотмена просроченных pending-платежей за мероприятия при ОБЫЧНОЙ записи (только лист ожидания); минимум 0,65 ₽ / максимум 1500 ₽ комиссии СБП не учитываются.
- **Ловушка (моя ошибка)**: правка метода через Python-замену по ДИАПАЗОНУ (`s[s.index(a):s.index(b)]`) удалила 4 соседних метода `YookassaService` — упало на проде «Call to undefined method». После любой замены по диапазону проверять `grep -c "function X"` для всех методов файла. Отладка платежей — `storage/logs/laravel.log` прода, строки `OnlinePaymentController::start`.

## Платежи и кошельки
- PaymentService — создаёт Payment при записи (методы: cash, online, wallet)
- YookassaService — онлайн-платежи, вебхук: YookassaWebhookController
- VirtualWallet — wallet_id per (user_id, organizer_id), баланс в минорных единицах (balance_minor / 100)
- WalletTransaction — типы: credit / debit; PaymentSetting — payment_hold_minutes (дефолт 15)
- OrganizerSubscriptionService — подписки организаторов (не путать с абонементами игроков)

### Авто-запись на мероприятия (Premium, добавлено 2026-08-24)
- Модель `PremiumAutoBooking` (таблица `premium_auto_bookings`: user_id, event_id, position; unique(user_id,event_id)) — «джоб»: привязан к СЕРИИ (event_id), не к конкретному occurrence, срабатывает при открытии регистрации на КАЖДЫЙ будущий тур, пока не удалён. До 5 штук на пользователя (`PremiumAutoBookingController::MAX_JOBS`).
- Доступны только индивидуальные форматы (обычные + `tournament_individual` + `king_beach`); `team_classic`/`team_beach` исключены и в поиске, и в `store()` (там своя логика формирования команд, не подходит под простую позицию).
- UI — новый блок на `/premium/settings` (`premium/settings.blade.php`): поиск мероприятия по ID или названию локации (`GET /premium/auto-bookings/search-events`, эталонный autocomplete-паттерн + учёт приватности через `EventVisibilityService`), позиции подтягиваются вместе с результатами поиска (без отдельного запроса) и заполняют `<select>` через `createCustomSelect()` destroy+recreate (CLAUDE.md — перезаполнение `<option>` не подхватывается кастомной обёрткой само по себе).
- При создании (`store()`) — `EventRegistrationGuard::checkStaticEligibility()` (новый публичный метод, БЕЗ проверки окна регистрации/занятости — окно ещё не открыто, это нормально) проверяет возраст/личные данные/уровень/жёсткий гендерный допуск позиции по ближайшей будущей occurrence серии. Не проходит — джоб не сохраняется, ошибка пользователю.
- Триггер — `premium:auto-booking` (`everyFiveMinutes`, тот же паттерн окна `[registration_starts_at ∈ now-5мин..now]`, что и `subscriptions:auto-booking`) → `PremiumAutoBookingJob($occurrenceId)`. Бронирование — advisory lock (`pg_advisory_xact_lock(occurrence_id, crc32(position))`) + `EventRoleSlotService::tryTakeSlot()`, как в `EventRegistrationController::persistRegistration()` (`AutoBookingSubscriptionJob` тоже защищён с 2026-08-27, коммит `41c56e9d`: `persist()` под тем же `pg_advisory_xact_lock(occurrence_id, 0)` + повторная проверка дубля и вместимости перед INSERT; ранее эта строка ошибочно утверждала обратное). Платные мероприятия — обычная логика `PaymentService::createForRegistration()`, оплата отдельно от подтверждения участия.
- **Приоритет абонемента**: `SubscriptionService::hasUsableAutoBookingSubscription()` — если у игрока есть активный абонемент с авто-записью на это же мероприятие, `PremiumAutoBookingJob` пропускает пользователя (не бронирует) независимо от порядка выполнения команд `subscriptions:auto-booking`/`premium:auto-booking` в один тик планировщика — абонемент отрабатывает свою же job.
- **Подтверждение участия за 12 часов** (увеличено с 5 часов 2026-09-03): `event_registrations.premium_auto_booking_id` (FK, nullOnDelete) + `premium_auto_confirm_deadline_at` (= `now()+12h` на момент бронирования, НЕ привязано к `created_at` — важно при реактивации старой отменённой регистрации, где `created_at` был бы датой из прошлого). Подтверждение — существующий генерик-роут `POST /registrations/{registration}/confirm` (`routes/web.php`, уже использовался для абонементов), без изменений. UI подтверждения — блок на `events/show/players.blade.php` (`@elseif($myReg->premium_auto_booking_id && !$myReg->confirmed_at)`, по образцу подписочного блока рядом).
- Команда `premium:expire-auto-bookings` (`everyFiveMinutes`) отменяет неподтверждённые (`confirmed_at IS NULL`, `premium_auto_confirm_deadline_at <= now()`) через Eloquent `save()` (не Query Builder — иначе `EventRegistrationObserver` не вызовет `WaitlistService::onSpotFreed()`), уведомляет игрока.
- **Баг (исправлен 2026-08-30): игрока выписывало повторно после самостоятельной перезаписи**. `EventRegistrationController::persistRegistration()` при `$existing` (реактивация СТАРОЙ, ранее отменённой строки `event_registrations` для того же `user_id+occurrence_id` — обычный путь при повторной самостоятельной записи) сбрасывал только `status/is_cancelled/cancelled_at/position/payment_*`, но НЕ трогал `premium_auto_booking_id`/`premium_auto_confirm_deadline_at`/`confirmed_at`/`subscription_id`/`subscription_usage_id`/`auto_booked`/`coupon_id`/`coupon_discount_pct`, оставшиеся от ПРЕДЫДУЩЕЙ жизни этой же строки (авто-запись премиум/по абонементу). Сценарий: игрок не подтвердил премиум-авто-запись → `premium:expire-auto-bookings` отменил регистрацию → игрок сам записался снова (реактивировал ту же строку) → `premium_auto_booking_id`/просроченный `premium_auto_confirm_deadline_at` остались висеть → следующий прогон `premium:expire-auto-bookings` (каждые 5 мин) тут же матчил эту строку заново (`is_cancelled` уже `false`, `confirmed_at` всё ещё `null`, дедлайн в прошлом) и отменял её повторно — хотя игрок записался сам, без всякой авто-записи. Фикс — в блоке `if ($existing)` явно обнулять все 8 полей авто-записи/абонемента/купона перед `save()`, трактуя реактивацию как полностью новую самостоятельную запись. **Не исправлено попутно** (отдельная, более мелкая проблема, не была в жалобе пользователя): если игрок при такой реактивации всё же передаёт `subscription_id`/`coupon_code` (форма записи это умеет), логика применения абонемента/купона (`Приоритет 1/2/3`) целиком находится в ветке создания НОВОЙ строки (после `return;` для `$existing`) — на реактивированной строке абонемент/купон молча не применится.
- `PremiumService::expireAll()` при истечении подписки удаляет и `PremiumAutoBooking` (по образцу уже существовавшего удаления `PlayerFollow`) — фича только для активного премиума.
